## What Went Well

**Pure helper extraction made alerting testable end-to-end (Story 9-3):** `buildAlertValues()` and `runFailureSequence()` are pure (or near-pure) functions extracted from the flush path. This made it possible to test the two-part post-condition Dana flagged in the Epic 8 retro — "flush_manifest writes the error row AND publishes to `alerts:flush_failure`" — as a single L1 test driving both functions through a fake flusher, without standing up B2 or QuestDB.

Dana (QA Engineer): "The two-part post-condition test was exactly what I asked for. The key is that `runFailureSequence` is the single code path that does both writes. Testing it directly means both sides of the condition are in one test. If you split them, you could pass both tests but still have a bug where one side calls the wrong method."

**`computeShadowLag` pure function — lag logic testable without Redis (Story 9-4):** The shadow lag formula (`n - 1`, clamped to 0) was extracted into a pure function `computeShadowLag(n int64) int64`. The three L1 tests — zero when caught up, positive when behind, zero when no entries — run without a Redis client, miniredis, or any setup. The 100ms timeout context wrapping `ShadowLag()` in `stateFunc` is tested separately.

Amelia (Developer): "The `n - 1` formula looks trivial until you ask: what does XRange return when the consumer is exactly caught up? It returns one entry — the current message itself. So lag = 1 - 1 = 0. That off-by-one is invisible in an integration test that only checks the 'behind' case. `computeShadowLag(1) == 0` is the specific assertion that would have caught a naive `return n` implementation."

**FORCE_SIGKILL test mode in deploy script (Story 9-4):** The deploy script includes a `FORCE_SIGKILL` environment variable that bypasses the graceful SIGTERM/drain sequence and immediately kills the old slot. This is used to test XAUTOCLAIM recovery — if orphaned messages are handled correctly under SIGKILL, they're handled correctly under any failure mode. The test mode is part of the shipped script, not a separate test fixture.

Winston (System Architect): "Shipping the test mode in the production script is the right call. It means every future deploy engineer has the SIGKILL recovery path available without hunting for a separate test harness. The safety comment in the script explains why the SIGKILL path still produces correct behavior via XAUTOCLAIM."

**AbortMultipartUpload fresh context — correctly implemented (Story 9-2):** The Epic 8 retro flagged this as the most common mistake in upload timeout handling. In 9-2, `AbortMultipartUpload` explicitly uses `context.Background()`, separate from the upload's `context.WithTimeout` context. The test verifies abort is called even when the upload context is cancelled.

Alice (Product Owner): "The fresh context requirement is one of those things that's obvious once you understand it — a cancelled context rejects all calls, including the abort. But it's invisible in happy-path testing. The fact that we called it out in the Epic 8 retro and it showed up correctly implemented in 9-2 is exactly how retro action items are supposed to work."

## Challenges and Patterns

### 1. `XAutoClaim` Returns Three Values, Not Two (Story 9-4)

**What happened:** Initial implementation of `XAutoClaimPending()` used `result, err := c.rdb.XAutoClaim(...).Result()`, expecting a struct return. The actual signature returns `([]redis.XMessage, string, error)` — messages, next cursor, and error as three separate values. After fixing to `result, _, err`, `result.Messages` failed to compile because `result` is already `[]redis.XMessage`, not a struct with a `Messages` field.

**Why it matters:** The go-redis `XAutoClaim` API differs from `XReadGroup` and `XRange` in its return type. The documentation lists the return as matching Redis's XAUTOCLAIM reply structure, but the Go binding unpacks it differently than the XREAD/XRANGE bindings.

Amelia (Developer): "The fix was two lines — unpack the three values correctly and iterate `result` directly. But the compiler error message ('result.Messages undefined') doesn't point at the root cause, which is the incorrect two-value unpack. It took reading the go-redis source to confirm the three-value signature."

**Root cause:** API surface inconsistency — `XRead`, `XRange`, and `XAutoClaim` all have different return signatures in go-redis. When in doubt, read the interface definition, not the documentation.

**Lesson:** For go-redis methods with non-obvious return shapes, check the interface definition directly. `XAutoClaim` returns `([]XMessage, string, error)`; `XRead` returns `[]XStream`; `XRange` returns `[]XMessage`. They look similar but are not interchangeable.

### 2. HTTP Handler Goroutine vs. Consumer Goroutine Data Race in Promotion Design (Story 9-4)

**What happened:** Initial `promoteFn` implementation — called from the HTTP handler goroutine via POST /promote — directly called `e.aw.acc.Reset()`, `e.aw.openDepthSet = false`, and `e.c.XAutoClaimPending()`. These operations access state exclusively owned by the consumer goroutine. The code review identified 4 High severity data races.

**Why it matters:** The consumer goroutine is the sole writer for `acc`, `ob`, `seenIDs`, `tickCount`. The HTTP handler goroutine reading or writing these fields without synchronization is an unsynchronized concurrent access — a data race even when the race detector doesn't fire immediately, because the timing-dependent window is narrow.

**Fix:** All post-promotion work was moved into `Run()`, executed by the consumer goroutine after `runShadow()` exits. `promoteFn` (HTTP goroutine side) only calls `promoted.Swap(true)` and `c.Promote(c.LastShadowID())`. The consumer goroutine detects `shadowMode.Load() == false` at the top of `runShadow()` and exits, returning control to `Run()`, which then performs `acc.Reset()`, `seenIDs` clear, `tickCount = 0`, and `XAutoClaimPending`.

Winston (System Architect): "The design principle is: the consumer goroutine exclusively owns all accumulator and book state. Anything that touches that state must either be called from the consumer goroutine or protected by a mutex. Moving post-promotion cleanup to `Run()` is the right fix — it makes ownership explicit in the code structure, not just in comments."

Dana (QA Engineer): "The review caught 4 High items in promotion design in a single pass. That's the highest severity concentration in any story this project. The adversarial review format — three independent reviewers covering blind spots, edge cases, and AC compliance — is what surfaced all four together rather than one at a time."

**Lesson:** When a goroutine owns state, treat that ownership as a hard boundary. Functions called from external goroutines (HTTP handlers, promotion callbacks) must not cross the boundary without explicit synchronization. `atomic.Bool` is safe for flag signals; accumulator state is not.

### 3. `lastShadowID` vs. `xreadCursor` Separation for Spec Compliance (Story 9-4)

**What happened:** Initial implementation used `lastShadowID` for both the exposed `LastShadowID()` API and the internal XREAD cursor. Before any messages arrived, both were `"0-0"`. The spec contract for `LastShadowID()` states it returns `""` before the first message is processed. Returning `"0-0"` violated the contract and would cause `Promote()` to set the wrong consumer group cursor: `"0-0"` instead of `"$"`.

**Why it matters:** `Promote()` handles `lastShadowID == ""` by using `"$"` as the consumer group cursor — meaning the new group starts from the stream tip and doesn't replay history. If `lastShadowID` is `"0-0"` (never `""`), this branch is never taken, and the group is created at position `"0-0"`, causing the new consumer to replay the entire stream from the beginning.

**Fix:** Two separate fields — `xreadCursor string` (internal, initialized to `"0-0"`, updated on every XREAD) and `lastShadowID string` (exposed via `LastShadowID()`, initialized to `""`, updated only when a message is processed by `handleShadowMessage`). The split costs one struct field and zero complexity in the hot path.

Amelia (Developer): "The `""` vs `'0-0'` distinction is a two-character difference that has correctness implications for the entire stream replay behavior. Separating the fields makes each one's purpose unambiguous: `xreadCursor` is the XREAD start position; `lastShadowID` is the last message the shadow consumer successfully processed."

**Lesson:** When an internal cursor value and an exposed API value start at different sentinel values, use two separate fields. Don't unify them to save a field — the merge point is the bug.

### 4. Code Review Patches to Flusher Tests (Story 9-3)

**What happened:** Review of 9-3 identified three test-quality issues: (1) string slice truncation using `msg[:512]` operates on bytes, not runes — truncating a multi-byte UTF-8 character mid-sequence produces invalid UTF-8; (2) `ts` field assertion used `assert.NotEmpty` instead of asserting the exact expected epoch millisecond value; (3) type assertions for `errMsg` and `ts` fields lacked ok-flag guards, so a wrong type would panic rather than fail cleanly.

**Fixes applied:**
```go
// Rune-safe truncation
if runes := []rune(msg); len(runes) > 512 {
    msg = string(runes[:512])
}

// Exact ts assertion
assert.Equal(t, "1746489600000", ts)

// Ok-flag guards
errMsg, okMsg := fields["error_msg"].(string)
assert.True(t, okMsg, "error_msg must be a string")
ts, okTs := fields["ts"].(string)
assert.True(t, okTs, "ts must be a string")
```

Dana (QA Engineer): "The byte-vs-rune truncation is the most consequential of the three. Alert messages can contain exchange error strings with non-ASCII characters — a mid-rune truncation would produce a malformed string that fails JSON serialization downstream. The ok-flag guards are test hygiene; the rune-safe truncation is production correctness."

**Lesson:** String truncation by index (`s[:n]`) is byte truncation, not character truncation. For any string that may contain non-ASCII content, use `[]rune(s)[:n]` and convert back. This applies to both production code and test assertions that construct strings from external inputs.

## Key Insights

1. **Consumer goroutine exclusive ownership is load-bearing for correctness.** All accumulator, order book, and seen-ID state is owned by the consumer goroutine. Any code that touches this state must run in that goroutine. Post-promotion cleanup belongs in `Run()`, not in the HTTP handler. Violations are data races even when the race detector doesn't fire immediately.

2. **Pure functions for non-trivial formulas enable isolated L1 tests.** `computeShadowLag(n)` and `buildAlertValues()` are pure — zero setup, direct assertion. The off-by-one in lag (`XRange returns 1 entry when caught up`) and the two-part post-condition in alerting were caught cleanly in L1 without any infrastructure.

3. **Sentinel value contracts must be enforced by field separation.** When `LastShadowID()` returns `""` before first message and the internal cursor starts at `"0-0"`, collapsing them into one field produces a silent correctness bug. Field separation is cheaper than the bug.

4. **Adversarial code review finds concurrency design flaws.** The promotion goroutine boundary violation was a design-level issue, not a typo. The 4 High findings in one story (9-4) are the highest severity concentration this project saw. Three-perspective adversarial review (blind spots, edge cases, AC compliance) is effective for concurrency-heavy stories.

5. **Byte truncation is not character truncation.** Any truncation of strings that may contain non-ASCII content must use `[]rune`. This applies everywhere an attacker or exchange feed can supply the string, not just in tests. The flusher patch is the canonical example.

6. **Test the SIGKILL path, not just graceful shutdown.** XAUTOCLAIM recovery after SIGKILL requires the cursor loop to handle > 1000 orphaned messages. A test that only covers SIGTERM doesn't validate XAUTOCLAIM at all. Shipping FORCE_SIGKILL in the production script means this path is always available.
