## Challenges and Patterns

### 1. UTC Weekly Boundary — Sunday vs. Monday Edge Case (Story 8-1)

**What happened:** The 1w bar must close at Monday 00:00:00 UTC. `time.Truncate` doesn't know about weeks (Go's `time.Duration` has no "week"). The implementation used:
```go
daysBack := int(t.Weekday())  // Sunday=0, Monday=1, ..., Saturday=6
if daysBack == 0 {
    daysBack = 7  // Sunday: go back 7 days to previous Monday
}
daysBack--  // Monday: 0 days back; Tuesday: 1 day back; etc.
```
This correctly maps: Monday → 0 days back (today is the boundary), Tuesday → 1 day back, …, Sunday → 6 days back to previous Monday.

**Why it matters:** If `daysBack == 0` for Sunday isn't handled, Sunday becomes the boundary instead of Monday. All weekly bars would be off by one day, and the Sunday bar would never close. Silent — the weekly bar would just keep accumulating.

Amelia (Developer): "The Go `time.Weekday()` values are Sunday=0 through Saturday=6 — not Monday=0 as some conventions use. The special case for Sunday is the only non-obvious line in the whole weekly boundary calculation."

**Root cause:** Go's `time.Weekday()` puts Sunday at 0, which breaks the naive `daysBack = int(t.Weekday()) - 1` formula. The fix requires an explicit Sunday guard.

**Lesson:** For calendar-based UTC boundaries that don't map to `time.Truncate`, write the boundary calculation as a pure function and test it exhaustively for all 7 days of the week, including both Sunday (edge) and Monday (identity). Test at both 00:00:00 UTC (at the boundary) and 23:59:59 UTC (one second before the next boundary).

### 2. `hasNewTicks` Carry-Across-Bar-Boundary (Story 8-2)

**What happened:** The `hasNewTicks` flag in the consumer goroutine tracks whether any ticks arrived since the last partial publish. When a bar closes, `hasNewTicks` is set from the tick-processing path and then consumed by the close signal path. Depending on timing, `hasNewTicks` can be `true` at the moment of bar close from ticks that arrived in the current second — causing one extra `PublishPartialBar` call immediately after `PublishBars` for the closed TFs.

**Is this a bug?** No. `PublishPartialBar` guards on `bar.OpenTs == 0` — if the cascade accumulator has just been reset for a new bar (not yet seeded), the publish is silently skipped. The extra call is harmless. The alternative — resetting `hasNewTicks` explicitly on bar close — would add state management complexity for no observable benefit.

Winston (System Architect): "The `OpenTs == 0` guard is load-bearing here. It's not just an efficiency check — it's the correctness guard that makes the post-close hasNewTicks carry safe. The code review flagged it as informational, which is correct."

**Lesson:** When a flag can carry state across a signal boundary (tick path → close path), document the invariant that makes the carry safe. In this case: "PublishPartialBar skips on OpenTs == 0, so stale hasNewTicks after bar close is always safe." Without the guard, the carry would be a correctness bug.

### 3. `accumulator.Bar` vs. `cascade.Bar` for ob_features (Story 8-3)

**What happened:** The `ob_features` stream must publish the OB close state — `BestBid`, `BestAsk`, depth fields, OFI. These fields live on `accumulator.Bar`, not `cascade.Bar`. `closedBars` (from `engine.Fold()`) is a `[]cascade.Bar` with 9 OHLCV fields. Passing a `cascade.Bar` to `PublishOBFeatures` would have compiled but silently omitted all 12 OB fields.

**How it was caught:** The story dev notes explicitly state: "Why `bar` not `closedBars` for ob_features?" with a detailed explanation. The correct call is `publisher.PublishOBFeatures(aw.ctx, bar)` where `bar` is the `accumulator.Bar` from `acc.CurrentBar()`.

Alice (Product Owner): "The type mismatch protection comes from the method signature: `PublishOBFeatures(ctx context.Context, bar accumulator.Bar)` accepts only `accumulator.Bar`. If someone passed a `cascade.Bar`, it wouldn't compile. The type system carries the intent."

**Lesson:** When two struct types have similar names (`accumulator.Bar`, `cascade.Bar`) and live in the same function scope, the method signature is the primary protection against confusion. Keep method signatures typed to the precise struct required — avoid `interface{}` or over-generic argument types that would permit wrong-type calls to compile.

## Key Insights

1. **Numbered flush sequence steps prevent ordering errors.** When a sequence has 6+ steps and ordering is critical for correctness (BarReset must be last), numbering the steps in the story spec makes the implementation unambiguous. The step numbers survived all the way into code comments.

2. **Purity contracts (no time.Now(), no goroutines, no init()) enable direct testability.** Both `cascade` and `writer/redis` are pure packages. Their tests run without mocks for clocks or goroutine orchestration. The constraint is enforced by convention (package doc comment), not compiler.

3. **Calendar boundary edge cases need exhaustive day-of-week tests.** The Sunday edge case in weekly boundary calculation would be invisible in a test that only checked "a Monday." Seven-day coverage is the minimum for weekly boundaries.

4. **Type-safe method signatures are a free safety check.** `PublishOBFeatures(bar accumulator.Bar)` rejects `cascade.Bar` at compile time. When two struct types are structurally similar, the compiler is a better guard than runtime assertions.

5. **Clean reviews trace to detailed dev notes.** Both 8-2 and 8-3 passed with zero required patches. The dev notes for both stories specified exact field tables, exact key name formats, and exact error-handling patterns. The review had nothing to find because the spec left no ambiguity.

6. **Import cycle risk analysis should be documented, not just resolved.** Adding `accumulator` to `writer/redis` was safe because `accumulator` is a leaf node. Documenting this reasoning means the next engineer who adds a dependency to `writer/redis` has a reference point for what cycle checks to run.

## Epic 9 Preview: Cold Storage & Operations

Amelia (Developer): "Epic 9 is the final epic — daily Parquet flush to Backblaze B2, flush failure alerting, and blue-green deployment. Architecturally, this is new territory: file IO, cloud uploads, and multi-slot orchestration."

**Stories in scope:**
- 9-1: Flush manifest DDL
- 9-2: Daily Parquet flush and catch-up
- 9-3: Flush failure alerting
- 9-4: Blue-green deployment

**Key design constraints:**
- Catch-up on startup reads `last_flush_date` from Redis first; falls back to `flush_manifest` for Redis-reset scenarios — must not silently lose data on Redis reset
- Upload timeout is 4h via `context.WithTimeout`; on cancellation, `AbortMultipartUpload` must be called with a **fresh context** (not the cancelled one)
- Blue-green uses `lastShadowID`-anchored XREADGROUP promotion — not stream tip, not `>`
- XAUTOCLAIM must cover old slot's orphaned messages at promotion time

Winston (System Architect): "The `AbortMultipartUpload` with a fresh context is the most common mistake in upload timeout handling. If you use the cancelled context for the abort call, the abort itself fails silently. The story dev notes must be explicit about this."

Dana (QA Engineer): "I want to see a simulated B2 failure test that verifies `flush_manifest` writes the error row AND publishes to `alerts:flush_failure`. That's a two-part post-condition that's easy to test only one side of."

Alice (Product Owner): "Blue-green is the one story where correctness is hard to verify in isolation. The `shadow_lag=0` readiness gate is the key metric — make sure it's exposed in `/health` before the deploy script tries to use it."

**Risks for Epic 9:**
- Parquet serialization: need to verify zstd + Hive partitioning works with the QuestDB export path
- Blue-green XAUTOCLAIM timing: if old slot SIGKILL happens before XAUTOCLAIM, orphaned messages must be recovered — must test the SIGKILL path, not just graceful shutdown
- `flush_manifest` is a new QuestDB table — migration must run before any flush code executes; migration runner from Epic 5 handles this
