## What Went Well

**1. get_message(timeout=1.0) was the right approach for stop unblocking.**
The spec proposed using `punsubscribe()` in `stop()` to unblock `ps.listen()` — but that technique is architecturally incorrect (PUNSUBSCRIBE on a new Redis connection has no effect on the original listener). Using `get_message(timeout=1.0)` instead makes the thread self-checking: it exits the poll loop within 1s of `_stop_event` being set, with no dependency on a separate connection. Cleaner than the spec and correctly implements the 2-second AC.

**2. REST fallback refactored from open-orders to fills endpoint.**
The old fallback used `get_open_orders` which could only return open/partially-filled orders — a fill that arrived during WS downtime was permanently missed. Replacing it with `get_recent_fills` backed by the fills endpoint means fills are recovered regardless of order status, matching the WS path exactly.

**3. 26-4 doc-only scope was correctly scoped.**
The original D2 deferred item assumed KuCoin and Bybit POST responses return a creation timestamp. They don't. Resolving by documentation (comment in place_order + strike-through in deferred-work.md) was exactly the right call — no behavior change needed.

**4. Code review caught 5 real bugs before shipping.**
Adversarial review found: auth failure permanent lockout, `_last_fill_ts_ms` not advancing in fallback loop, `instanceServers` IndexError, `list[Any]` type annotation error, and backoff reset misplaced. All 5 were clean patches with no design decisions required. None were obvious during implementation.

**5. Public method refactor (get_private_ws_token) improved encapsulation.**
Removing `_get_ws_token` from `KuCoinPrivateFeed` and replacing it with a public method on `KuCoinRESTClient` is a cleaner boundary — the WS feed was previously coupling to the REST client's internal `_request` API. The test now verifies the public contract, not the internal path.

## What Did Not Go Well

**1. Spec described a non-functional stop unblocking approach.**
The story spec proposed creating a separate Redis connection in `stop()` to send `punsubscribe` — this would not unblock the original listener. Implementing this per-spec would have introduced a false sense of correctness (tests might pass if the unsubscribe arrived in the brief window before get_message was called). Spec deviation was necessary but took extra diagnosis time.

**2. `_auth_failure_count` permanent lockout not caught during implementation.**
After the RuntimeError was raised at count=5, the counter stayed at 5. Every subsequent reconnect attempt immediately raised RuntimeError again — permanent lockout. This is a HIGH severity bug that was only caught by the adversarial review. The pattern of "reset counter after using it as a trigger" is easy to miss.

**3. `_last_fill_ts_ms` not advanced in REST fallback path.**
The fallback loop delivered fills correctly but never advanced `_last_fill_ts_ms`. So every poll re-fetched the same window from `_last_fill_ts_ms` (or the 30-minute fallback), creating growing redundant API calls and dedup work. Only caught in code review.

## Lessons Learned

**1. When deviating from spec, document the alternative immediately in the code.**
The `get_message(timeout=1.0)` approach differs from the spec's `punsubscribe` suggestion. Without a comment explaining why `listen()` wasn't used, a future reader might try to "improve" it back to the spec approach and reintroduce a non-functional stop mechanism.

**2. Counter-reset patterns need a specific test case.**
Auth failure escalation needed two tests: "escalation fires at exactly N" AND "counter resets after escalation so recovery is possible." The first test was written; the second was added only after the review discovered the permanent lockout. Test ACs for counter-based features should include reset/recovery cases explicitly.

**3. Fallback paths must maintain ALL tracking invariants, not just dedup.**
When the REST fallback delivered a fill, it correctly added to `_seen_fill_ids` but forgot to advance `_last_fill_ts_ms`. The general rule: any fill delivery path (WS or REST) must update every piece of tracking state that the other path updates. A checklist for "what does `_handle_ws_fill` update?" should guide implementing the fallback equivalent.

**4. Always verify what `_request` returns before trusting spec response paths.**
The Acceptance Auditor's three false positives (KuCoin/Bybit response unwrapping, token parsing) all came from the spec showing raw API response paths while `_request` already unwraps the envelope. Before writing new methods, check whether `_request` returns raw JSON or the pre-unwrapped data dict.
