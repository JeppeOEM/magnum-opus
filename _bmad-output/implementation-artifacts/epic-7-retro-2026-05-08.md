## What Went Well

**blockwindow package isolation (Story 7-2):** The rolling 99th-percentile threshold was implemented in its own `internal/blockwindow` package with no dependencies beyond standard library. `Window` is a pure value type with a clean API: `Add`, `Threshold`, `Sizes`, `Restore`. Redis persistence lives in `accWriter.Flush` — the window package has no IO knowledge. The Epic 6 lesson "rolling window state in separate buffer" was internalized correctly.

Amelia (Developer): "The Redis persistence pattern for blockwindow also turned out clean — DEL + RPUSH pipeline on every bar close, LRANGE on startup. The `Restore` method makes the startup path read like documentation."

**Review process caught two runtime correctness bugs (Story 7-4):** The 3-parallel adversarial reviews surfaced:
1. The OB activity gate was `hasOBActivity || hasQuoteActivity` — the `|| hasQuoteActivity` arm caused trade-only bars to write zero-valued OB counters instead of nil. Silent data-quality bug.
2. Missing `HasLevel`-after-gap test — the `HasLevel` method returned stale data after `ApplyGap` reset the book, but no test covered this path.

Both would have been invisible in production: the gate bug silently writes 0 where NULL should appear; the HasLevel gap bug silently returns false-positive (level "exists" when book was reset).

Winston (System Architect): "The gate bug is particularly insidious because `hasOBActivity || hasQuoteActivity` reads like it should be correct — 'write OB fields if there was any activity.' But 'any activity' over-matches. The review forced the question: 'what does a bar look like with only trade ticks and no OBEvent calls?' and that revealed the issue."

**Import cycle prevention pattern (Story 7-4):** The `OBEventKind` type lives in `consumer`; `Accumulator` exposes `IncrementOBAdd/Cancel/Modify` as plain counter methods; `accWriter` bridges between them. This avoids `accumulator` importing `consumer`. The pattern is now established and documented in the dev notes.

Alice (Product Owner): "I remember being worried that the OBEventKind pipeline would get messy. The three-layer pattern — consumer derives kind, accWriter translates, accumulator increments — is actually easy to follow."

**`hasTicks` semantic clarity (Story 7-5):** The `OFI` nil semantics were cleanly separated from `hasQuoteActivity`. A bar with no ticks should have nil OFI; a bar with only trade ticks (no OB deltas) should have non-nil OFI with ofiSum=0. The `hasTicks` boolean gates this correctly without overloading existing flags.

**SeedFromLastKnown correctness (Story 7-5):** The carry-forward design for empty-second null rows is precise: only `hasOpenQuote` is set, not `hasCloseQuote`. This means downstream consumers see a non-nil open bid/ask for context, but nil close bid/ask — which correctly signals "no ticks this second." The asymmetry was intentional and documented.

## Challenges and Patterns

### 1. Pre/Post Ordering Error in bestBidChanges (Story 7-4)

**What happened:** The tracking block for `bestBidChanges`/`bestAskChanges` was placed AFTER `a.bestBid = bid` in `Apply()`:
```go
a.bestBid = bid; a.bestAsk = ask  // assignment first
if a.hasQuoteActivity {
    if bid != a.bestBid { a.bestBidChanges++ }  // always false — comparing bid to itself
}
```
After the fix, the tracking block is placed BEFORE the assignment:
```go
if a.hasQuoteActivity {
    if bid != a.bestBid { a.bestBidChanges++ }
    if ask != a.bestAsk { a.bestAskChanges++ }
}
a.hasQuoteActivity = true
a.bestBid = bid; a.bestAsk = ask  // assignment after
```

**Impact:** `bestBidChanges` and `bestAskChanges` were always 0. Silent — not a panic, not a compile error. Would have written plausible-looking zeros to QuestDB forever.

**Root cause:** The implementation spec (AC 9 of 7-4) stated "compare BEFORE updating `a.bestBid`/`a.bestAsk`" but the implementation reversed the order. This is a pre/post condition error — the kind that passes code inspection without careful reading.

Amelia (Developer): "The test caught it immediately — `assert.Equal(t, 1, *bar.BestBidChanges)` got 0. So the failure was visible in the test run. But if we hadn't written an explicit test for the increment behavior, it would have gone unnoticed."

**Lesson:** For state tracking that requires comparing to a previous value, the sequence — "read old, compare, update, write new" — must be stated and tested. Tests for change-count fields must include a tick that actually changes the value and assert > 0.

### 2. OB Activity Gate Over-Matching (Story 7-4, Review Finding)

**What happened:** `CurrentBar()` initially used `if a.hasOBActivity || a.hasQuoteActivity` to gate the 5 OB counter fields. A bar with only trade ticks (valid quotes, no OBEvent calls) would enter this branch and write 0 for all OB counters.

**Impact:** `bid_order_arrivals=0, ask_order_arrivals=0, bid_cancel_count=0, ask_cancel_count=0, ob_modify_count=0` instead of NULL for trade-only bars. This pollutes the dataset — a consumer cannot distinguish "no OB activity" from "zero OB activity this second" vs. "bar had ticks but no OB data available."

**Root cause:** The original story spec (AC 9) also had the over-matching gate. The review caught the data-quality implication that the spec itself had missed.

Dana (QA Engineer): "This is a reminder that if the spec has the bug, implementing the spec correctly still produces the bug. The review has to be willing to question the spec, not just check the implementation against it."

**Lesson:** For nullable fields representing optional data, "gate on exactly the condition that makes the field meaningful" — not a superset. Adversarial reviews should question whether nil-vs-zero semantics are correct for each new field group, not just whether the implementation matches the spec.

### 3. Interface Blast Radius (Story 7-3) — Continued from Epic 6

**What happened:** Adding `tsMs int64` to `AccumulatorApplier.Apply()` required updating: the interface definition, `accWriter.Apply()`, `Accumulator.Apply()`, `stubAcc.Apply()` in test, and all 30+ `acc.Apply(...)` call sites in `accumulator_test.go`.

**Impact:** Large mechanical cascade. Multiple compile errors before any logic was tested. Time spent is non-trivial but the work is correct and unavoidable.

**Root cause:** Same root cause as `side string` in 7-1. The `AccumulatorApplier` interface is the blast epicenter; every new parameter touches it.

Winston (System Architect): "The interface has grown from Apply(price, size, isTrade) to Apply(price, size, isTrade, side, tsMs, prevBid, prevBidSz, prevAsk, prevAskSz, currBid, currBidSz, currAsk, currAskSz). Fourteen parameters. This is a signal that the interface is doing too much, but restructuring it mid-epic would create more churn than it solves. I'd flag this for consideration in a future refactor after Epic 8."

Alice (Product Owner): "Can we batch the last expected parameters before Epic 8 starts, so we don't have another cascade mid-epic?"

Amelia (Developer): "Epic 8 doesn't add new Apply() parameters — the cascade engine works at bar-close granularity, not per-tick. So we should be safe."

**Lesson:** The interface blast is a known cost. Epic 8 doesn't add further Apply() parameters — document this so the Epic 8 dev agent doesn't get surprised mid-implementation.

### 4. barCount Semantics: BarReset vs. Reset Interaction (Story 7-5)

**What happened:** `BarReset()` increments `a.barCount++` at the end (after `CurrentBar()` reads it). But `Reset()` — called on gap/reconnect — calls `BarReset()` as its first step, which would increment barCount before zeroing it. The fix: `Reset()` must explicitly zero `a.barCount = 0` AFTER calling `BarReset()`.

**Impact:** Without the fix, the first bar after a gap would start at barCount=2 instead of 1 (since BarReset was called from Reset).

**Root cause:** `BarReset()` and `Reset()` have a dependency: `Reset` reuses `BarReset` to avoid code duplication. But `BarReset`'s new increment side-effect contradicts the semantic purpose of `Reset` ("start fresh"). The two levels of reset (bar boundary vs. gap/reconnect) must be kept conceptually distinct.

Winston (System Architect): "The BarReset/Reset two-level split has served us well, but every time we add state to BarReset, we have to ask: 'does Reset want this too?' For `barCount`, the answer is no. For `lastKnownBid`, the answer is also no. Documenting the rule: BarReset clears per-bar accumulators; Reset clears everything including cross-bar carry-forward state."

**Lesson:** When `Reset()` delegates to `BarReset()` and then needs to undo one of its effects, add an explicit override statement and a test. The rule "BarReset = bar boundary, Reset = full restart" must be applied field-by-field when adding new state.

### 5. Welford 3rd Moment Edge Cases (Story 7-3)

**What happened:** Realized skewness uses `M3/n / (M2/n)^(3/2)`. When `nMidReturns < 3`, nil. When `M2 == 0` (zero-variance: all returns identical), `(M2/n)^(3/2) = 0` — division by zero → nil. The nil condition requires checking `nMidReturns >= 3 && M2 > 0`.

**Root cause:** Not a bug — the nil conditions were specified correctly and implemented correctly. But the edge case (all mid-price returns equal within a 1-second bar) is realistic during low-volatility periods.

Amelia (Developer): "The test for `M2 == 0` skewness nil required setting up a bar where all three ticks had identical mid-price. Easy to do in isolation, but easy to miss in production if only tested with random data."

**Lesson:** Statistical edge cases (zero variance, identical timestamps, empty data) must all have explicit tests. Welford-based fields need tests for: n=0, n=1, n=2, n=3, all-equal values, and typical mixed values.

## Key Insights

1. **Pre/post ordering errors are invisible until tested.** `bestBidChanges` always returning 0 would have produced syntactically valid output with consistently wrong data. Tests that assert incremented counts (not just nil/non-nil) are the only safeguard.

2. **Gate conditions should match the field's semantics exactly.** `hasOBActivity || hasQuoteActivity` over-matches. For nullable fields, the gate must be "this field has meaningful data" — not "some related activity occurred." The adversarial review process earns its place here.

3. **Interface blast radius is a known cost, not a surprise.** The `AccumulatorApplier.Apply()` parameter list is now 14 items. This is the accumulated cost of additive development. Epic 8 does not add more — plan any future refactor deliberately, not reactively mid-epic.

4. **BarReset/Reset interaction needs a decision rule per field.** The rule: "BarReset clears per-bar accumulators; Reset clears everything including cross-bar carry-forward." When adding new state, categorize it at creation time — not when the interaction bug surfaces in a test.

5. **Import cycle prevention via translation layer works.** `OBEventKind` in `consumer`, `IncrementOB*` in `accumulator`, `accWriter` as translator. This pattern is established and reusable for any future event-type classification that `consumer` owns but `accumulator` shouldn't see.

6. **The rolling window isolation was correctly anticipated.** blockwindow is cleanly separated and could be replaced or extended without touching the accumulator at all. The Epic 6 retro action item paid off.

## Epic 8 Preview: Multi-Timeframe Cascade & Redis Output

Amelia (Developer): "Epic 8 is architecturally heavier than anything we've done so far. Let me walk through what's coming."

**Stories in scope:**
- 8-1: Cascade engine and clock boundary
- 8-2: Redis candle stream publisher
- 8-3: OB feature snapshot publisher

**Architecture:**
- **1s → 1m → 5m → 15m → 1h → 4h → 1d → 1w** cascade
- Bar-close signal via `time.Ticker` goroutine with a capacity-1 channel — consumer drains its batch before processing the close
- Partial bar publish cadence: every 250ms per symbol (`CANDLE_PARTIAL_PUBLISH_MS`)
- Accumulator state persisted to Redis (`candle:acc:{exchange}:{symbol}:{tf}`) as a HASH on each 1s close
- Startup reconstruction from QuestDB `snapshot_1s` rows since last closed boundary
- `ob_features:{exchange}:{symbol}` stream published on each 1s bar close

Winston (System Architect): "The capacity-1 channel for bar-close signals is the key safety mechanism. No mutex, no race — the consumer goroutine drains its current batch, then handles the close signal. Single-goroutine-per-symbol means we never have concurrent bar access."

**Dependencies on Epic 7 work:**
- All 67 `snapshot_1s` fields now correctly computed and nil-guarded
- `BarReset()` / `Reset()` semantics fully documented and tested
- `accWriter.Flush()` is the correct extension point for cascade

**Key risks for Epic 8:**
- Cascade accumulator persistence is new complexity: HASH serialization of Accumulator state to Redis requires careful field selection (don't serialize transient mid-bar state)
- QuestDB unavailable on startup: must increment `candle_cascade_cold_start_total{reason="questdb_unavailable"}` and log ERROR — higher-timeframe bars will be wrong until next boundary
- UTC boundary correctness: 1d at 00:00:00 UTC, 1w at Monday 00:00:00 UTC — must test near boundary conditions explicitly
- Weekly bar duplicate key: `XADD` to both `candles:1w:{exchange}:{symbol}` and the standard key — downstream must subscribe to exactly one

Dana (QA Engineer): "The simulated QuestDB-unavailable startup test is going to be important. That failure path must be tested explicitly — it's an ERROR-level log condition and must increment a specific metric."

Alice (Product Owner): "The partial bar cadence being time-based (not tick-based) is the right call. We don't want 10,000 Redis writes per second on active symbols. But 250ms means every bot gets at most 4 updates per second per symbol per timeframe. That's plenty for trading decisions."

**Action items before Epic 8 story creation:**
1. The `Apply()` interface has 14 parameters — Epic 8 does NOT add more Apply() parameters (cascade works at bar-close granularity). Document this explicitly in the Epic 8 stories so the dev agent doesn't attempt to extend the interface.
2. Accumulator HASH serialization strategy needs to be defined upfront in the 8-1 dev notes — which fields survive restart, which don't.
