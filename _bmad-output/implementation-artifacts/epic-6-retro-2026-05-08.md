## What Went Well

**Pure features package discipline (all stories):** Every new function — `MidPrice`, `Spread`, `EffectiveSpreadContrib`, `ComputeDepthSnapshot`, `DepthTo1PctBid`, `DepthTo1PctAsk` — is stateless and takes float64 or map inputs, returns values. All running sums live in the accumulator. This made every function independently testable with table-driven cases and no mocking.

**Story 6-1 as quality gate:** Starting Epic 6 with a fixture test that replays a realistic 20+ tick sequence validated the OB state machine before any feature code was written. The cold-start filter, seq deduplication, and TopNDepth correctness were confirmed before building on top of them.

**BarReset / Reset two-level split (6-2):** Separating bar-boundary resets from gap/snapshot full resets — with `lastKnownOB` surviving bar boundaries but cleared on gap — was a clean design. It correctly carries forward OB quotes into quiet bars with no OB activity, matching the architecture intent.

**bug fix caught at story creation (6-2):** The `IncrementGap()` was implemented but never called in the consumer EventGap handler. Story 6-2 spec included this as an explicit task, and it was caught and fixed. The gap_count field was always 0 before — now correct.

**Review process finding semantic errors (6-4):** The adversarial review caught that `DepthTo1PctBid` was missing an upper bound (`p <= bestBid`) — levels above bestBid were being summed incorrectly. Similarly for asks missing a lower bound. These are silent semantic bugs that unit tests written by the same developer would easily miss. The adversarial review earned its place again.

## Challenges and Patterns

### 1. Semantic Errors in 1-Pct Functions (Story 6-4)

**What happened:** Initial implementations of `DepthTo1PctBid` and `DepthTo1PctAsk` set a threshold but did not enforce the other bound:
- `DepthTo1PctBid`: checked `p >= bestBid*0.99` but omitted `p <= bestBid` — levels above best bid were counted
- `DepthTo1PctAsk`: checked `p <= bestAsk*1.01` but omitted `p >= bestAsk` — levels below best ask were counted
- `bestBid <= 0` guard used `== 0` instead of `<= 0` — negative prices not protected

**Impact:** Wrong values would have been stored silently for every bar. The fix was correct: `p >= lo && p <= bestBid` and `p >= bestAsk && p <= hi`.

**Root cause:** The story dev notes specified the one-sided threshold correctly, but the two-sided range semantics (half-open interval anchored at best quote) were not spelled out. The developer implemented only the stated constraint.

**Lesson:** For market microstructure features where the semantics are "within a window anchored at best price," story dev notes must state BOTH bounds explicitly. Single-bound description invites single-bound implementation.

### 2. Unconditional Zero Write for 1-Pct Fields (Story 6-3 Finding, Fixed in 6-4)

**What happened:** Story 6-3 review found that `DepthTo1PctBid`/`DepthTo1PctAsk` were initially placed unconditionally inside `hasCloseDepth` without the `HasBidVolume`/`HasAskVolume` guard, meaning a cold-start bar with an empty OB would write `ptr(0.0)` instead of `nil`.

**Impact:** QuestDB would write 0.0 instead of NULL for those columns — confusing downstream analysis (0 volume available vs. unknown/no data).

**Root cause:** The dev notes said "always populate both when `hasCloseDepth`" — which is correct for most depth fields (zero volume is a real value), but the 1-pct fields follow the same guard pattern as `WeightedBidPrice`/`WeightedAskPrice`. The dev notes did not distinguish.

**Lesson:** When adding new fields alongside existing guarded fields, document which guard condition applies to each new field explicitly.

### 3. `accumDepth` Sentinel Fragility (Story 6-3 Finding, Fixed in 6-4)

**What happened:** The original `accumDepth` implementation used `if l2 == 0` and `if top10 == 0` as sentinels to detect "not yet set" for the L2 and Top10 tier caps. If a book had exactly 0 volume at those tiers (legitimate but unusual), the cap would fire incorrectly.

**Impact:** Low in practice (books rarely have exactly 0 volume at L2 while having non-zero L1), but a latent correctness bug. Fixed to `n := len(levels); if n < 2` and `if n < 10`.

**Root cause:** Using value-0 as sentinel for "not reached yet" — a classic bug pattern. The fix (count-based check) is unambiguous.

**Lesson:** Use count/flag variables for "not yet reached" state, never zero-value of the accumulator variable.

### 4. Interface Churn from Adding `side string` (Story 7-1, Observed in Epic 6 Context)

**What happened:** Adding `side string` to `Accumulator.Apply()` required threading it through the entire call chain: `AccumulatorApplier` interface → `accWriter.Apply()` → `Accumulator.Apply()` → all test stubs. Every caller and every test stub had to be updated.

**Impact:** Several compile errors cascade-fixed before tests ran. The change was mechanical but had broad blast radius.

**Root cause:** The `AccumulatorApplier` interface is the junction between consumer and accumulator. Each parameter addition requires coordinated changes across three or four files.

**Lesson:** When planning stories that add new parameters to Apply(), note the interface-propagation scope explicitly. Consider batching related parameter additions into one story to minimize churn.

### 5. Test Value Aliasing (Story 6-3 Finding)

**What happened:** The `TestAccumulator_SetOpenDepth_PopulatesOpenFields` test used identical values for BidTop10 and AskTop10 (both 7.0), making it impossible to detect a field swap in `CurrentBar()`.

**Impact:** Low (caught in review before real swap was introduced), but the test was providing false confidence.

**Root cause:** Test data written quickly without checking that all asserted fields have distinct values.

**Lesson:** Accumulator struct tests — especially those validating field mapping from source struct to Bar — should use distinct values for every field to detect assignment to the wrong target.

## Key Insights

1. **Adversarial review catches semantic bugs that unit tests written by the same developer won't.** Both the `DepthTo1Pct` bound errors and the sentinel fragility were not caught by the implementation tests. The reviewer asked "what does this skip?" and found the answer.

2. **Dev notes that specify only one bound of a two-sided constraint invite one-sided implementations.** For financial features with range semantics, state both bounds and the anchor explicitly.

3. **Interface parameter additions have blast radius.** Every new parameter in `Apply()` touches 4+ files. Plan stories to batch parameter additions or document the scope clearly so the dev agent doesn't cascade-break incrementally.

4. **Distinct test values catch field-swap bugs.** When asserting that struct fields are correctly mapped to another struct's fields, use values that uniquely identify each field.

5. **The fixtures-first approach (6-1) paid off.** Having verified OB correctness before building any features meant that when features tests passed, we could trust the underlying data. No OB bug surfaced during 6-2 through 6-4.
