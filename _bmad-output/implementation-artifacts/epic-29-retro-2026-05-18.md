## What Could Be Better

**1. `split(":")` on address strings recurs across the codebase.**
This is the third time a string split on a network address caused a crash-on-edge-case bug (Epic 28: `int(result.get("totalPage", 1))` on null; here: `split(":")` on port-free host). The standard library's `str.partition()` is almost always the right tool for splitting on a possibly-absent separator. This should be a reflex, not a discovery.

**2. REST endpoint without unit tests shipped to review.**
Story 29-3 implemented `POST /backtest/validate` and `GET /backtest/validate/{run_id}` but no unit tests for the new routes were included. The acceptance criteria explicitly stated "Unit tests: mock QuestDBFeed construction; assert run_walk_forward and generate_validation_report called with correct parameters" — this was not done. Five tests were added as review patches. This repeats the same pattern from Epic 27's `/backtest/run`.

**3. Monte Carlo input was architecturally wrong from the story spec.**
The spec said to "collect per-trade P&L via a custom Analyzer" but also suggested using `fold.sharpe * fold.max_drawdown` as a proxy in the interim. The proxy is dimensionally invalid (Sharpe × drawdown has no unit) and produces noise, not P&L samples. The spec should have flagged this explicitly as "invalid proxy; prefer fold OOS P&L until `_TradeListAnalyzer` is implemented." Instead, the wrong proxy was implemented and caught in review.

**4. `_TradeListAnalyzer` was deferred without a clear trigger.**
The story spec acknowledged that per-trade P&L requires a `bt.Analyzer` subclass, then deferred it without specifying when it matters. Monte Carlo's statistical power scales with sample count — 3 folds vs. 300 trades is a significant difference. The deferral note should specify "fix when n_splits < 10 and the Monte Carlo output is used for a deployment decision."

## Patterns from Story Analysis

**Recurring review finding: missing REST endpoint tests.**
This appeared in Epic 27 (no tests for `/backtest/run`) and Epic 29 (no tests for `/backtest/validate`). Pattern: any new route added to `main.py` must have at least: happy-path test, 404 test, path traversal test. Write them before marking the story ready-for-review.

**Defensive string splitting habit not yet internalized.**
`split()` used instead of `partition()` on a potentially separator-free string. The fix is always the same: `host, _, rest = addr.partition(":")`. This is mechanical — it should not require a code review to catch.

**Design ambiguity in story specs leads to wrong implementations.**
Monte Carlo proxy was underspecified. When a spec says "use X as a proxy for Y," it should state whether X is dimensionally compatible with Y. A one-line dimensional analysis ("sharpe is unitless, drawdown is a ratio, their product is not P&L") would have prevented the patch.

**Zero bugs in walk-forward or stress-test computation paths.**
All review patches were in infrastructure (string parsing, tests, Monte Carlo input). The core validation logic in `run_walk_forward`, `run_stress_test`, and `generate_validation_report` was correct and clean.

## Lessons Learned

**1. Use `str.partition()` for any split on a potentially-absent separator.**
`split(":")` on a string without `:` returns a one-element list; `partition(":")` always returns a 3-tuple with empty strings for missing parts. Every network address, URL component, or header field that might lack the separator should use `partition`. Write it on first draft, not after review.

**2. New REST endpoints need tests before the story is ready-for-review.**
The pattern is: happy-path test, 404 test, path traversal test. This has now been flagged in two consecutive epics (27 and 29). Add these tests as part of the story implementation, not as review patches.

**3. Dimensionally validate proxy values in specs.**
When a spec proposes "use X as a proxy for Y," verify units. `sharpe × max_drawdown` is not P&L. Add a one-line dimensional annotation to the spec: "units: [currency]" or "units: [dimensionless]". If the proxy is invalid, do not implement it — use the closest valid approximation and document the limitation.

**4. Generalize defensive patterns beyond their original domain.**
Epic 28 taught defensive numeric casting; Epic 29 needed defensive string splitting. Both stem from the same principle: external inputs (API responses, config strings) can be in forms that naive conversions don't handle. A checklist for any function that parses external input: "What happens if the separator is absent? What if the value is null? What if the value is a float string?"
