## What Could Be Better

**1. Pagination was implemented without safety bounds.**
Both loops started as `while True` with only API-response conditions to break. A misbehaving API returning a perpetual cursor or large `totalPage` would loop indefinitely. The safety guard should be the first line of any unbounded network-driven loop, not a code review afterthought.

**2. `int()` cast on an untrusted API field is fragile.**
`int(result.get("totalPage", 1))` assumes the field is always a Python integer. The KuCoin API could return a string, a float, or null. Using `int(float(... or 1))` is more defensive. This class of cast-without-validation recurs across the codebase (same pattern appeared in Epic 27's `run_at_ns` bug).

**3. Spec vs. implementation divergence on market order fix (28-2).**
The story spec proposed `_last_fill_price` as the reference price for market orders. The actual implementation used `portfolio_value_usd` (a better approach that was already in place). The spec should have been written to describe the existing behaviour rather than a hypothetical fix. When a deferred item is "confirmed already fixed," update the spec to match reality before writing the story.

**4. Story 28-4 spec was written against a wrong assumption.**
The spec assumed the consumer lag Grafana panel didn't exist. It did. The discovery cost some context-reading to confirm. Lesson: before writing a story that adds infrastructure (panels, tables, endpoints), verify the infrastructure doesn't already exist.

## Patterns from Story Analysis

**Recurring review finding: unbounded loops with network calls.**
This appeared in both 28-3 (KuCoin) and 28-3 (Bybit) — 2/4 stories had the same class of bug. Pattern: whenever writing a `while True` loop driven by an external response condition, add a `MAX_ITERATIONS` guard as the first non-trivial line.

**Test coverage gap: spec boundary conditions.**
Story 28-1's drawdown=1.0 AC was explicitly stated in the spec but not tested. Pattern: when a spec says "X should equal Y when Z reaches its limit," that limit case needs its own test. Don't test only the happy path and a partial case.

**Zero bugs in ILP write path or circuit breaker** (noted in 28-1 review).
The gauge update code was inserted at the right place in `handle_fill` with no interference to existing paths. This reflects clean separation in `order_worker.py`.

## Lessons Learned

**1. Default to bounded loops for any network-driven iteration.**
Rule: `while True` loops driven by external state need a `MAX_ITERATIONS` guard as the first line. Write it before the loop body, not after a code review finds it missing.

**2. Cast untrusted API response fields defensively.**
`int(field)` crashes on null or "1.0". Use `int(float(field or default))` for numeric API response fields. This pattern recurred from Epic 27 — it's a systemic habit to fix.

**3. When a deferred item is "already fixed," describe the existing fix in the story.**
If D-15-2-3 was fixed via `portfolio_value_usd` approach, the story spec for 28-2 should document that approach and add verification tests — not re-propose a different `_last_fill_price` mechanism. Spec-vs-implementation divergence leads to confusion in code review.

**4. Check for existing infrastructure before specifying "add X".**
Before writing a story to add a Grafana panel, run a quick `grep` or JSON scan to confirm the panel doesn't exist. 5 minutes of discovery prevents a story that's already done.

**5. Boundary conditions in specs must have corresponding tests.**
If the spec explicitly states a boundary value (drawdown=1.0 when all gains lost), write the test for that exact boundary. The review will otherwise flag it as untested, requiring a patch.
