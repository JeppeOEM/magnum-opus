## What Went Well

**1. `_TF_TABLE` constant isolated in backtest package.**
Copied from `base.py` rather than imported — keeps the backtest package self-contained with no runtime dependency on the bot service's strategy layer. The duplication is intentional and documented.

**2. Runner is pure compute — no side effects.**
`run_backtest()` returns a `BacktestResult` dataclass and writes fills via the existing `BacktestResultWriter`. All QuestDB persistence of runs/equity/snapshots happens in the REST layer (27-4). This separation made 27-3 (CLI) trivially reuse the runner without a service dependency.

**3. Dashboard polling pattern is clean.**
`dcc.Store` for `run_id` + `dcc.Interval` that self-disables on terminal state (done/failed) is the right Dash idiom. No busy-polling after completion.

**4. `EquitySampler` produces NaN for unsampled bars.**
Returning `float("nan")` for non-sampled bars (rather than repeating the last value) correctly marks where no measurement was taken. `collect_equity` then skips NaN entries, so the equity curve only contains actual sample points.

## What Did Not Go Well

**1. Critical correctness bug shipped in 27-1 DDL schema.**
P2+P3: `_fetch_snapshot` added a `tf_filter` when extending to multi-TF, not realising that `snapshot_1m` and `snapshot_15m` have no `tf` column. This caused a column-not-found failure for every non-1s backtest — the entire motivation for the multi-TF work. The bug was not caught by unit tests because the feeds tests used mocked HTTP responses that didn't simulate the real schema difference.

**2. Two security issues from string interpolation habit.**
P4 (SQL injection in `/backtest/runs`) and P5 (path traversal in `/backtest/run`) both stem from the same habit: using f-strings to build SQL/paths from user input. These should have triggered a security mental-model check at authoring time. Neither was caught by tests.

**3. Broad exception catch masked bugs.**
P8: `except Exception` in `collect_equity` was written as "safety net" but would have hidden any `AttributeError`, `TypeError`, etc. in the observer line access path. Exception scope should match the specific expected failure mode.

**4. TOCTOU on file read (P7).**
Hash was computed from the file, then code was read separately — two filesystem reads with a window between them. If a file was modified between the hash call and the read call, the stored snapshot wouldn't match the executed code. Fixing this required one atomic read before spawning the task.

## Lessons Learned

**1. When adding a WHERE clause on a new table, verify the column exists in that table's schema.**
The `tf_filter` bug came from copying a query pattern from `snapshot_1s` to the multi-TF path without checking the target schema. Rule: diff the DDL of every table you query before reusing a filter.

**2. Any user-supplied value going into SQL or a file path needs validation before use.**
Two security patches from the same root cause. Before calling `f"WHERE strategy_name = '{name}'"` or `strategies_dir / name`, ask: can this string contain `'; DROP TABLE` or `../../etc/passwd`? If yes, sanitise first.

**3. Exception catches should be the smallest scope that covers the expected failure.**
Write the catch for the one exception you expect. If you're not sure what to expect, let it propagate — a crash with a traceback is more useful than silent wrong behavior.

**4. Atomic read for hash + code snapshot.**
Any time you hash a file and also want to store its content, do one read, hash the bytes, store the same bytes. Never hash then re-read.
